User Space vs. Kernel Space
• User Space:
• Runs user applications.
• Limited access to hardware.
• Uses system calls to request kernel services.
• Kernel Space:
• Executes privileged operations.
• Directly manages hardware and resources.
• System Calls: The bridge between user and kernel space.

## Page 26

Kernel Space and User Space (cont)
User space code is what you run from the command line
• either as a user or as root.  
• typically are programs that you write in 'C' or other languages, compile and 
execute
Kernel space code is used for purposes such as 
• low level OS routines and scheduling  (Kernel)
• basic I/O access to the hardware (via Kernel modules)
Kernel memory and code space is protected from the user
• user space program can only access the kernel space through executing system 
calls (e.g. open() )
In fact, some program functions (e.g. fopen() ) provided  by standard library (e.g. 
glibc)
• actually execute the appropriate system calls behind the ‘scene’. (e.g. fopen() is 
a ‘wrapper’ for syscall open(). )

## Page 27

Loadable Kernel Module
Loadable Kernel module (LKM) is a piece of code that can be loaded and unloaded 
into the kernel space upon demand at run time
•
hence extend the functionality of the kernel without the need to reboot the 
system
One type of LKMs that we will study here is the device driver
•
which allows the kernel to access hardware connected to the system – more on 
this later
Without modules, we would have to build monolithic kernels and add new 
functionality directly into the kernel image
•
lead to larger kernels as new functionalities are added.
•
require us to rebuild and reboot the kernel every time we want to add new 
functionality – time consuming.

## Page 38

Macros ‘_ _init’ & ‘_ _exit’ 
__init macro
• Marks a function as initialization-only. For built-in drivers (compiled into the kernel): The function is used only during 
system startup. 
• Its memory is freed after initialization, reducing kernel memory usage. 
• For loadable kernel modules (LKMs): The function is executed when the module is loaded.
__exit macro
• Marks a function as cleanup/exit code.
• For LKMs:
• The function is executed when the module is unloaded (e.g., via rmmod).
• For built-in drivers:
• The function is not needed and is omitted to save space.
MODULE_LICENSE("GPL") 
• Declares the module’s license. Accessible via tools like modinfo. Important because: Indicates the module complies with 
GPL (free software). 
• Allows access to certain GPL-only kernel symbols. 
• Helps the kernel determine whether the module is “tainted”.

Module Handling Issues
Important information:
1. Only the root user can load/unload modules.
2. Module and kernel version numbers are VERY important.
3. If your module crashes it might take down the kernel.
4. These days you need to decide if your modules are
    GPL'd or not, otherwise they will taint the kernel

• meaning that any problems/bugs experienced will   
    be less likely to be investigated by the maintainers.

Module License and Symbols
Based on the metadata indicated in its MODULE_LICENSE()
• a module could be declared as GPL-licensed module
A function (e.g. func1()) declared in kernel (and modules) can be made visible 
(i.e. exported) to other modules using the macros:
• EXPORT_SYMBOL(func1) 
But can restrict a function (e.g. func2()) to be visible only to GPL-licensed 
module, by using the macro:
• EXPORT_SYMBOL_GPL(func2)
Hence can restrict the functions that a non GPL-licensed module can access.

3. But how do we continue to communicate between spaces once the

## Page 56

Registering a Module
We will stick with character devices here.
When an LKM is loaded, the first thing it does is to register with the kernel to “own” 
a particular device major number.
The kernel module function to register a module (which is declared in <linux/fs.h>) :
    register_chrdev(MAJOR_NUM, DEVICE_NAME, &fops)
Side note: A special case is when MAJOR_NUM = 0, then the    kernel  can dynamically 
allocate a MAJOR number using        
                     alloc_chrdev_region(). 
Very useful for some architectures which are running out of    MAJOR numbers!
To remove the driver from the system:
     unregister_chrdev(MAJOR_NUM, DEVICE_NAME)

## Page 57

Major and Minor Numbers
Whenever there is a command to access a device by a user space  program, i.e. to 
open, read from or write to the device file
• the kernel looks at the MAJOR number 
• and then looks in its internal registry to find the module that has registered to 
handle that MAJOR number.
Hence the major number is used to identify the module (driver) associated with the 
device.
Kernel then passes control to the corresponding module, plus a pointer to a data 
structure with lots of info such as:
•
what is its MINOR number? 
•
number of chars requested/sent
•
pointer to memory holding/waiting for the chars

Module I/O Access
To handle the normal user space file request operations (via system calls) such as

The supported operations by a module

## Page 61

Basic Driver Methods
The open method is called when a file is opened
•
provided for a driver to do any initialization in preparation for later operations.
The release method is the reverse of open
•
which is to deallocate any data structure performed by open and then shut down the 
device.
The write method copies data from user space application code to kernel space device
The read method copies data from the kernel space device to user space application code.
For methods that are not implemented in a driver
•
the corresponding entries in the file_operations structure should be set to NULL (i.e. not 
declared)

## Page 72

Aside: mknod through udev
As mentioned, hardware devices are accessed through device nodes located in the 
/dev directory. 
•
traditionally, these special files were created at install time by the distribution, 
using the mknod command.
•
so /dev are populated with every device that might possibly appear in the 
system
A better way is to use the udev daemon to manage these /dev files dynamically 
at runtime
•
udev will create nodes when devices are detected and delete them when 
devices are removed (e.g. hotplug USB devices at runtime). 
•
hence the /dev directory contains only entries for devices which actually exist 
on the system at the current time (as opposed to devices which could exist.)
